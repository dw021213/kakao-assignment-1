# 3차 과제 설계 기획서

코드를 짜기 전에 "무엇을 어디에 둘지"를 먼저 정한 문서예요. (= AI에게 던지기 전의 plan)
2차(React + 로컬스토리지) 앱을 3차(Next.js App Router + FastAPI) 구조로 **그대로** 옮기는 게 목표예요.
→ 2차의 CRUD·상태 필터뿐 아니라 **일간/주간 날짜 뷰까지** 옮겨요. (운영자 제공 예시 코드의 방향과 일치)

## 1. 프론트 vs 백엔드 책임 분리

2차에서는 프론트 혼자 데이터까지 들고 있었어요(로컬스토리지). 3차에서는 데이터를 서버가 관리해요.

| 일 | 2차 (React) | 3차 (Next.js + FastAPI) |
| --- | --- | --- |
| 데이터 저장 | 브라우저 로컬스토리지 | FastAPI + SQLite DB |
| CRUD 로직 | 프론트 `useState` 조작 | 백엔드 엔드포인트 |
| 상태 필터·검색 | 프론트에서 배열 `filter` | **백엔드에서 DB 조건 조회** |
| 날짜(주간/선택일) | 프론트 상태 | 프론트 상태(뷰 상태) + 항목의 `date`는 DB 저장 |

## 2. 백엔드 API 설계

데이터 모델은 `id / title / completed / date` 네 개예요. `date`는 "YYYY-MM-DD" 문자열로, 어느 날의 할 일인지 저장해요. (2차의 날짜 기능을 옮기기 위함)

| Method | URL | 설명 |
| --- | --- | --- |
| GET | `/todos` | 목록 (`?filter=active\|completed` + `?search=키워드` 서버 필터) |
| POST | `/todos` | 생성 (`title`, `date`) |
| GET | `/todos/{id}` | 단건 조회 (수정 페이지에서 사용) |
| PUT | `/todos/{id}` | 수정 (보낸 필드만 변경) |
| DELETE | `/todos/{id}` | 삭제 |

- **상태 필터·검색은 서버(DB)에서** 처리해요 (도전 미션 1·2 요구사항). `filter`는 `completed` 조건, `search`는 제목 `ilike`.
- **날짜 필터는 클라이언트에서** 해요. 서버는 그 날 todo만 주는 게 아니라 (필터·검색을 통과한) 전체를 주고, 화면이 선택한 날짜로 추려요. → 주간 뷰의 "요일별 개수 배지"를 한 번의 응답으로 계산할 수 있어서 이 방식이 자연스러워요. (예시 코드와 동일한 선택)
- DB 모델(`Todo`)과 요청/응답 스키마(`TodoCreate/Update/Response`)를 **분리**했어요.

## 3. 화면 구조 — 목록은 단일 Client 보드

| 파일 | 종류 | 이유 |
| --- | --- | --- |
| `app/todos/page.tsx` | Server | `<Suspense>`로 보드를 감싸는 얇은 껍데기 |
| `app/todos/components/TodoBoard.tsx` | Client | 주간 뷰·날짜 선택·추가·검색·필터·토글·삭제 (인터랙션 덩어리) |
| `app/todos/new/page.tsx` | Client | 입력 폼 (날짜 지정 생성) |
| `app/todos/[todoId]/page.tsx` | Server | 수정할 Todo 하나를 서버에서 불러옴 (`actions.getTodo`) |
| `app/todos/[todoId]/components/EditTodoForm.tsx` | Client | 입력 폼 |
| `app/todos/loading.tsx` / `error.tsx` | Server / Client | 로딩·에러 경계 |

### 왜 목록을 Server 렌더가 아니라 Client 보드로?
- 명세 미션5 *텍스트*는 "목록을 `actions.ts`(서버)로 불러오라"고 하지만, **운영자가 준 예시 코드는 목록을 단일 Client 컴포넌트에서 직접 불러와요.** 둘이 어긋나요.
- 핵심은 "**필터·검색이 FastAPI(서버)에서 처리되는가**"이지, Next의 Server Component로 렌더하는가가 아니에요. 클라이언트가 `?filter=&search=`로 FastAPI에 요청하면 이미 "서버 필터링" 요구는 충족돼요.
- 주간 뷰의 `selectedDate`(선택한 날)는 인터랙션 상태라 클라이언트가 들어야 자연스러워요. 이걸 서버 렌더와 섞으면 "필터 URL 이동 시 선택 날짜가 날아가는" 버그가 쉽게 생겨요.
- 그래서 **목록은 예시 코드 방향대로 Client 보드**로 두고, `actions.ts`는 수정 페이지의 단건 조회에만 남겨요(미션5의 actions.ts 활용은 그쪽에서 지킴).

## 4. route.ts vs actions.ts

| | route.ts | actions.ts |
| --- | --- | --- |
| 역할 | 클라이언트 HTTP 요청을 FastAPI로 넘기는 **프록시** | Server Component가 직접 호출하는 서버 함수 |
| 이번 사용처 | 목록 조회(GET)·생성·수정·삭제 (클라이언트 → `/api/...` → FastAPI) | 수정 페이지의 단건 조회 |

- 클라이언트가 FastAPI(8000)에 바로 요청하면 **CORS 문제**·백엔드 주소 노출이 생겨서, 같은 출처인 `route.ts`(`/api`)를 거쳐요.

## 5. 적용한 학습 포인트 — 파생 상태(derived state)

2차 튜터 피드백: *"weekOffset을 별도 state로 들지 말고 selectedDate에서 매번 계산만 해라. 그러면 주/선택날짜가 어긋나는 충돌이 사라진다."*

- 그래서 이번엔 **`selectedDate` 하나만 상태로 두고, 보고 있는 주(`weekStart`)는 그 날짜에서 계산(파생)** 해요. `weekStart`라는 state 자체를 없앴어요.
- 예시 코드는 `weekStart`와 `selectedDate`를 **각각 따로** 들어서, 다른 주로 넘긴 채 선택일이 그대로면 둘이 다른 주를 가리킬 수 있어요(2차에서 멘토가 지적한 그 충돌). 파생으로 두면 그 상태 자체가 불가능해져요. → **예시보다 개선한 지점.**
- 대신 "이전/다음 주" 버튼은 보고 있는 주가 아니라 **선택한 날짜를 7일 옮기는** 동작이 돼요. (의도된 동작)
- 상태 필터·검색은 **URL(`?filter=`, `?search=`)** 로 둬서 새로고침·공유·뒤로가기에서 유지돼요.

## 6. 환경변수

| 변수 | 위치 | 노출 | 용도 |
| --- | --- | --- | --- |
| `NEXT_PUBLIC_API_URL` | frontend/.env.local | 브라우저 O | 클라이언트가 프록시(`/api`)를 부를 때 |
| `BACKEND_URL` | frontend/.env.local | 서버만 | route.ts·actions.ts가 FastAPI를 부를 때 |
| `DATABASE_URL` | backend/.env.local | 서버만 | DB 주소 |

## 7. 검증 계획 (코드 믿지 않기)

- **자동 테스트(pytest)**: 생성/조회/수정/삭제 + `filter=active/completed` + `search` + `date` 저장·응답을 `backend/test_main.py`에서 검증. (FastAPI `TestClient` + 인메모리 SQLite)
- **타입체크·린트**: `tsc --noEmit`, `eslint`.
- **수동**: 두 서버를 띄워 주간 뷰·날짜 이동·추가·검색·필터를 직접 클릭.
